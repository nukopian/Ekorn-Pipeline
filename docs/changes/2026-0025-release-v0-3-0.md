## Background

The release delivers the design of 2026-0022: sources, stages, gathers
and sinks, the lifecycle, the role methods, the words and the
operators. Most of it is new since v0.2.0, and DBIx-Squirrel, on its
`pipeline-experimental`, is so far its only user.

## Decisions

- [x] **D1.** Is this release v0.3.0, or v1.0.0? **v0.3.0,** Iain
  decided on 2026-11-13, letting it settle before switching to v1.0.0
  when the time is right. The design is settled, but most of what it
  delivers is unreleased, two parts of it changed on the day this was
  decided (2026-0026 and 2026-0027), and only DBIx-Squirrel has used
  it. Under 1.0, a change to what CLAUDE.md counts as behaviour, the
  messages among it, would be a v2.0.0, and one such change was
  already proposed: a message from DBIx-Squirrel of 2026-11-13 (its
  commit a3708534c87955d69d67887256503ad951957bbb), that `pipeline_in`
  give a named pipeline itself when given one name, which changes how
  stages are numbered in errors. Considered on the way to 1.0: settle
  what could break first, such as that suggestion, with a cold review
  of every public name and default; say what the 1.0 promise covers,
  perhaps leaving messages' wording free to change in minor releases;
  and ship a trial release DBIx-Squirrel depends on from CPAN, then
  v1.0.0 with no changes once the trial has run for a while.
- [x] **D2.** Do `docs/design/` and IMPLEMENTATION.md stay once v0.3.0
  is delivered, or go, their history kept in git and this item's
  record? **They stay on `pipeline-experimental`, and don't come to
  `develop`,** Iain decided on 2026-11-13: they're long, and reading
  them costs a session more than they now give. So the merge's last
  commit on `pipeline-experimental` removes `docs/design/`, which keeps
  them in the history, and the records that link to them say where
  they were. Until then, they aren't kept up to date with the code.
- [x] **D3.** Who drafts the README, rewritten for the stream concept,
  as the design's 20.1 has it: Iain, or Claude? **Claude,** as Iain
  asked on 2026-11-13; it was rewritten that day, in
  3b6804ef19eeda7702723a260f70ba68192b9d34, with every example run.
- [x] **D4.** How does `pipeline-experimental` reach `develop`, without
  `docs/design/`? **By a fast-forward, after one commit that deletes
  `docs/design/`,** Iain decided on 2026-11-13. `develop` has nothing
  of its own since the branch left it, so there's no merge commit.
  History isn't rewritten to take the folder out: 76 commits touch it,
  so every later hash would change, and DBIx-Squirrel's records and
  messages cite Ekorn's hashes. Two signed tags go first:
  `rollback/develop-2026-11-13`, on `develop` as it was
  (124a9a47e8ff8b573343cc27f429308e32920854), to reset it to if need be;
  and `archive/pipeline-experimental`, on the branch's last commit
  with `docs/design/`, which keeps the design reachable by name once
  the branch is gone. The branch is deleted only on Iain's word. Ekorn
  goes first; DBIx-Squirrel's `pipeline-experimental` merges into its
  `develop` after, as Iain will ask its session to.
- [x] **D5.** Does DBIx-Squirrel need v0.3.0 on CPAN, perhaps as a

  so. **No,** Iain decided on 2026-11-13: it tests against Ekorn's

- [ ] **D6.** Is v0.3.0 released as a trial first, now that it's ready?
  D5 decided DBIx-Squirrel needn't wait for one; Iain raised a trial
  again on 2026-11-14, to decide on 2026-11-15. A trial needs its own
  route: `minil dist` has no `--trial`, and `minil release`, which
  has, isn't used. The options: a version with an underscore, which
  sorts above v0.3.0, or a tarball named `-TRIAL`, with META's
  release status set to match, to be checked with PAUSE first.
- [x] **D7.** Does the last of 2026-0032's speed-up wait? Each pulled
  value enters two `try` blocks, about 0.07 µs each; one for both
  would save about 6% more on `next`, but means restructuring how the
  loop tells a source's error from a stage's (2026-0032's record, What's
  left). Before the release, or as an idea for after it? **Tried, and
  an idea for after,** Iain decided on 2026-11-14: done before the
  release, as he leaned to, it measured 1 to 2% faster with stages and
  6% slower with none, for a more intricate loop. Its record,
  [2026-0033](2026-0033-one-try.md), has the measurements.
- [x] **D8.** CLAUDE.md's Perl section says `use experimental
  qw(try)` "also allows `finally`", but on 5.36 `finally` compiles
  only after a `catch`, as 2026-0032 found. Correct it, and tell
  DBIx-Squirrel, whose CLAUDE.md says the same? **Yes,** Iain decided
  on 2026-11-14. Checked on every Perl CI covers: `try {...} finally
  {...}` is a syntax error on each, from 5.36 to 5.44, not only 5.36,
  and `try`/`catch`/`finally` compiles; under `use v5.40`, `try`/`catch`
  needs no line, but `finally` still warns that it's experimental.
  CLAUDE.md now says so, and DBIx-Squirrel was sent the same as a
  message.

## What happened

**The merge, 2026-11-13.** Steps 1 to 5 went as planned. The tags
went on 124a9a4 and e340785; b854fce deleted `docs/design/`, with its
four git-ignored PDFs, and pointed CLAUDE.md, MAINTAINING.md,
`t/15-proofs.t` and the records of 2026-0014 and 2026-0022 at the
tag. All tests passed and gitleaks found nothing, and `develop`
fast-forwarded from 124a9a4 to b854fce. Iain deleted the branch once
CI was green.

CI's first run of the branch's work, on b854fce, failed only its
style job: Perl::Critic takes a Perl's builtins from that Perl, and
`all` is a keyword from 5.42, so the iterator's `sub all` was flagged
on CI's 5.44, though it had passed by hand on 5.36. 8406050 marked it
as an exception, a method that can't be mistaken for the keyword, and
moved the style commands to 5.44, as CI runs them; CI passed on every
job. DBIx-Squirrel was told of the same gap in its commands.

**The docs' sweep, 2026-11-14,** the TODO task of 2026-11-13, done as
Iain asked: the reference's coverage first, in plain English, with
short lines filled, and every pipeline of two or more stages written a
stage to a line. DBIx-Squirrel's changes turned up nothing the docs
needed: it was fixing a bug in a sink of its own.

- **Coverage:** every method and function each module's POD
  documents, and every message in its DIAGNOSTICS, is in the
  reference; every public sub is named there but `DESTROY`, whose
  effect is documented. The Contents of the reference and the user
  guide list every section.
- **Developers' worked examples,** as Iain asked: a section, Making
  each kind of part, with a table of what each piece is called with
  and returns, and an example of each kind, run before it was
  written. Writing it showed one rule easy to get backwards, which
  the example now shows both ways: a stop at or after a stage cuts
  its input short (no flush, its end told `stopped`), and one before
  it doesn't. Two details the reference hadn't said: only a `gather`
  block may return a pipeline, not a role method, and a sink of one
  whose flush returns several values gives the first.
- **Old terms:** the iterator was still "the closure" in the
  reference and `iterator`'s POD, a flush was named `$end` in an
  example, and Stop's POD spoke of "end functions".
- **Pipelines a stage to a line:** 97 calls, by a script that changed
  only layout, checked by comparing each file's code with whitespace,
  trailing commas and comments set aside; and ten `|` chains, by
  hand, those that print keeping their result in a variable first, as
  `xt/howto.t` reads a printing line's comment only on that line. A
  list of the word `pipeline`'s forms became statements, each with its
  comment above.
- **Lines:** paragraphs that broke early, or ran past 74 columns, were
  filled again to 70, checked to change nothing but whitespace.

**The pre-release washup, 2026-11-14,** as Iain asked, of the code,
tests and docs, for consistency, coverage, omissions, errors,
inefficiencies, invented names and style.

- **Checked, and sound:** tests pass on 5.36 to 5.44, and CI on every
  commit; coverage of `lib/` is 100% of statements, branches and subs;
  `lib/` passes Perl::Critic, every file perltidy, and all POD
  podchecker. Every message the code raises is in its module's
  DIAGNOSTICS and the reference, and every DIAGNOSTICS entry is
  raised. Every `snake_case` name the docs give in code is defined, or
  an example's own, or JSON's or Ref::Util's. The how-to's examples run
  in `xt/howto.t`; each of the reference's 107 and the README's 15 was
  run on its own after the how-to's data, and those that didn't run
  are fragments, such as a synopsis's `@stages`, or use stand-ins,
  such as the README's `users()`, as they're meant to. No slop words,
  and no em dashes.
- **Fixed:** the how-to said only pushes through plain subs had been
  optimised, but 2026-0032 sped up pulls; a pull measured about 26
  times slower than `map` and `grep`, not thirty; and finding an
  iterator's code once saves about 0.02 s over 300,000 values, not
  0.03 s, in the reference and Iterator's POD. MAINTAINING.md gave
  DBIx::Squirrel's range as `>= v0.1.1, < v0.2.0`, which moved to
  `>= v0.2.0, < v0.3.0` on 2026-11-10. The main module's SEE ALSO named
  six modules of nineteen. Comments in Gather (from before flushes and
  ends had names), Sink and Operators (lines filled badly).
- **For Iain to decide:**
  - **Long sentences.** About ten in the prose run past 50 words, most
    in the reference: its "iterator" section (`my($x) = $next->()`),
    Named pipelines (`named` on a class always makes a new pipeline),
    How a run ends, and Flushes and ends; and the how-to's opening of
    chapter 4, and its warning about `sub {...} | sub {...}`. Some 100
    more pass 35 words. Splitting them is left until Iain's own read
    of the docs, so the two don't cross.
  - **`iterator`'s message.** Given what isn't a source, it croaks
    "Expected a code reference", though it takes any object offering
    `EKORN_SOURCE`, which is what 2026-0008 made messages say. A
    clearer one, such as "Expected a source: a code reference, or an
    object offering EKORN_SOURCE", is a change of message, which
    v0.3.0 can carry, with a word to DBIx-Squirrel. **Done,** as Iain
    asked on 2026-11-14, with that message; DBIx-Squirrel, whose
    `t/05-pipeline.t` tests it, was handed a task.
  - **The README's Acknowledgements** say "in collaboration with
    Claude", but not what Claude did, which CLAUDE.md asks of them.
- **Inefficiencies, for the optimisation that follows:**
  - Operators' `|` into a sink, and `@{}`, collect with a loop of
    `$next->()`, through the iterator's `&{}` overloading for every
    value, where its `all` gives every value in one call.
  - A chain's step, `sub () { $next->() }`, goes through the same
    overloading for every value.
  - A sink called directly, as a code reference, makes a new pipeline
    of itself at every call.
  - A pushed run copies its values twice: into the call's signature,
    then into `_push_steps`'s arguments.
  - A run with a part made for it costs about 26 µs to set up, against
    1.5 µs for a plain push, measured on a one-value run: some fifteen
    closures and the run's lists are made each time.
  - Each pulled value enters two `try` blocks, which 2026-0033 tried
    and set aside.
  - A stop goes through Carp's `croak`, which looks at its argument
    before dying with it; the cost is once a run, for most stages.
  - JSON's writers enter a `try` and call `print` once a value.
