## Background

Every DBIx::Squirrel iterator with stages adds a stage of its own,
`sub { $counter->{produced}++; $_[0] }`, last, or before the last if
that's a sink, only so its `result_number` can say which result a
stage is making. Each row pays a step for it. DBIx-Squirrel measured
it reading all 297,848 rows of a SQLite table through one bare stage,
best of five, ns a row, Ekorn at v0.3.4's code:

| | 5.36.3 | 5.44.0 |
|---|---|---|
| `next`, with the counting stage | 1,865 | 1,827 |
| `next`, without it | 1,664 | 1,570 |
| `all`, with it | 1,683 | 1,650 |
| `all`, without it | 1,451 | 1,396 |

So the stage costs 200 to 260 ns a row, 11 to 15%. It can't count
outside the run instead: its `next` doesn't see what `all` takes in
one call, or what a sink takes.

A run knows when a value leaves its last stage or reaches a sink, and
the value its source gave, so Ekorn can count results and keep the
original for any package's stages. DBIx::Squirrel::Context's POD says
what its two functions promise today:

- **`result_number`:** the number of the result being made, from 1.
  It counts results, not rows. While a stage drops rows, it stays the
  same. Each value a stage returns in place of one row is a result of
  its own. In a flush of a stage made with `gather`, it's the number
  of the first value the flush returns. It's there only in an
  iterator's own stages.
- **`result_original`:** the row the result is being made from, as it
  was fetched, before any stage changed it; undef in a flush of a
  stage made with `gather`, and the stages after it. It's kept in the
  run's context by the statement's source, so it's there wherever a
  statement is read, a chain's stages included.

## Decisions

- [x] **D1.** Where do the functions go, and how do they meet
  DBIx::Squirrel's? In a new module, Ekorn::Pipeline::Context, as
  `result_number` and `result_original`, as Iain decided on
  2026-11-16. DBIx::Squirrel::Context keeps functions of the same
  names, which shadow Ekorn's, built on them as DBIx-Squirrel's
  session designs, and DBIx::Squirrel::Tooling goes on importing its
  own, not Ekorn's: being a new module, Ekorn::Pipeline::Context
  reaches DBIx::Squirrel's users only if it's added to a list there.
  Why: what a stage asks of the run it's in is the run's, so any
  package's stages can ask it, and DBIx::Squirrel can drop its
  counting stage.
- [x] **D2.** What does `result_number` count, in each kind of run?
  What DBIx::Squirrel's promises, for every run, pulled or pushed, an
  iterator's `all` included: the run's results so far, plus one,
  where a result is a value leaving the last stage or reaching a
  sink. Each run counts its own, so a pipeline run inside a stage
  doesn't move its caller's count, and an iterator read as a source
  counts the results of its own run. undef outside a stage. As
  recommended, Iain decided on 2026-11-16: it's the promise
  DBIx::Squirrel's users have now, made good in every run.
- [x] **D3.** What is `result_original`, in each kind of run? As
  recommended, Iain decided on 2026-11-16: the value the run's own
  source gave, or that was pushed, that the result is being made
  from, before any stage changed it; the same for each value a stage
  returns in place of one; undef in a flush and the stages after it.
  For a run reading an iterator, it's the value the iterator handed
  out, not that iterator's own original. DBIx::Squirrel's shadow
  differs there: its rows are kept by the statement's source in the
  run's context, so its `result_original` reaches them through chains
  too. Why: each run answers for itself, as `result_number` does
  (D2), with nothing carried from one run to another, and a package
  that wants an original from further up the line, as
  DBIx::Squirrel does, carries it in its context. Iain first decided
  the other way the same day, that Ekorn's should be carried through
  iterators read as sources, as DBIx::Squirrel's row is, then went
  back to the recommendation before any work started.
- [x] **D4.** What may they cost a run whose stages don't read them?
  Nothing to measure, against v0.3.4, on 5.36 and 5.44, as 2026-0040
  halved a run's set-up; so the run's state is put where the
  functions can find it once a call, not once a value, and each value
  only counts and keeps its original, with no `local`. As
  recommended, Iain decided on 2026-11-16: most runs never ask.
- [x] **D5.** Exported by default, and in Ekorn::Pipeline::Tooling?
  `@EXPORT_OK`, as DBIx::Squirrel's, since the names are ones a
  caller's code might have; and in Tooling's tags, as a word a
  stage's author reaches for. As recommended, Iain decided on
  2026-11-16.
- [x] **D6.** Which version? A v0.3.x: a new module, and nothing that
  runs today changes, so it reaches DBIx::Squirrel's users with no
  release of its own, and it moves its counting stage over when it's
  ready. As recommended, Iain decided on 2026-11-16.

## The plan

**What:** Ekorn::Pipeline::Context, exporting on request
`result_number` and `result_original`, as D1 to D5 say, and
Ekorn::Pipeline::Tooling exporting both in a tag named `:context`, and
in `:all`. The tag has DBIx::Squirrel::Tooling's name for its own, so
its `xt/ekorn-tooling.t` passes as it is, and its `t/28-tooling.t`
still finds its own functions win, as D1 wants.

**Why:** D1: what a stage asks of the run it's in is the run's.

**How:** every run keeps a count of its results and the original of
the value going through its stages, in lexicals of the loop running
it, and puts a reference to them where the two functions find them,
once a call of the loop, not once a value (D4). A value waiting on
`@todo`, as a flatMap's second and later values do, carries its
original with it. A result is a value leaving the last stage, or a
value given to a sink's step. A flush's values, and those after them,
have no original. The three loops all do this: `_push_steps`, for a
pushed run of plain stages and a plain feed's push; `_plain_iterator`;
and `_full_iterator`, which runs every other run, feeds and sinks
included.

**Steps:**

1. Measure before: a pushed run, an iterator's `next` and its `all`,
   each through one plain stage and through a `gather` with a flush,
   on 5.36 and 5.44, at v0.3.10's code, best of five.
2. Write the spec as tests, in `t/32-context.t`: each kind of run,
   pushed, an iterator's `next` and `all`, a feed's pushes and close,
   plain and full; a stage that drops values and one that returns
   several; a flush, and the stages after it; a sink; a stop's
   carried values; undef outside a stage; a pipeline run inside a
   stage, and an iterator read as a source, each counting its own;
   and the run nested in itself, a stage of a run reading its
   functions from inside a run of the same pipeline.
3. Count and keep the originals in the three loops, and add the
   module, in `@Ekorn::Pipeline::Errors::INTERNAL` if it croaks.
4. Measure after, as in step 1; nothing measurable for a run whose
   stages don't read them, as D4 says, or the record says what it
   costs and why.
5. Tooling's `:context` tag; its POD, the reference and the how-to;
   the manuals remade; `Changes`.
6. A message to DBIx-Squirrel: the functions, what its shadows can be
   built on, and that its Tooling tests should pass as they are.

**Done when:** the tests pass on 5.36 to 5.44, coverage holds its
floors, step 4's measurements are in this record, and DBIx-Squirrel
has its message.
