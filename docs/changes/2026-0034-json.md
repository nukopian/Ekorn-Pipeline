## Background

JSON is the commonest way values reach a program, and leave it, as
documents or as JSON Lines. A module of one source and one sink for
it, each also a stage, is the first of Ekorn's own parts that needs a
module beyond Perl and Ekorn's dependencies. It's also an example of
the kind of module the how-to's chapter 10 tells others how to write:
one function making a different part by its options, from Ekorn's own
words, `source`, `gather` and `sink_one`.

## Decisions

- [x] **D1.** Which encoder? **JSON::MaybeXS,** Iain decided on
  2026-11-14: Cpanel::JSON::XS where it's installed, JSON::PP
  otherwise. It's a new runtime dependency, in `cpanfile`, which
  every user installs, whether they use JSON or not.
- [x] **D2.** What does a JSON file read by the `from_json` source look
  like? **It works it out,** Iain decided on 2026-11-14: "No friction.
  Just works." The input is read as a stream of documents, which covers
  JSON Lines, documents one after another, and one document. If the
  input holds exactly one document and it's an array, its elements are
  the values; otherwise each document is one. A `type` option, `json`,
  `jsonl` or `ndjson`, says instead: `json`, one document, an array
  giving its elements; `jsonl` or `ndjson`, each document as it is.
  An input that's one array is read whole before its elements are
  given, as which it is can't be known until it ends.
- [x] **D3.** When does it ship? **In v0.3.0,** Iain decided on
  2026-11-14, which now depends on it. It only adds, so DBIx-Squirrel's
  range is unaffected.
- [x] **D4.** What does the `to_json` sink write? **By `type`,** Iain
  decided on 2026-11-14: a file named `*.jsonl` or `*.ndjson` gets JSON
  Lines, any other one array, a valid JSON document; `type` says
  instead. A filehandle gets JSON Lines unless `type` says `json`.
  JSON Lines can't be indented, so an encoder that indents croaks.
- [x] **D5.** What does `to_json` pass on as a stage? **What a file of
  its `type` would hold,** Iain decided on 2026-11-14: `jsonl` or
  `ndjson`, the default, each value as one compact line of text, without
  its newline, ready for `to_file`; `json`, every value gathered, and
  passed on as one text, an array, at the end of the run.
- [x] **D6.** What does `from_json` give as a stage? **Each document in
  each text,** Iain decided on 2026-11-14: a text with one document gives
  it, as `decode_json` does, and a chunk of JSON Lines each line's. An
  array is one value, not unpacked, so a column holding one isn't split.
  With `type => 'json'`, each text is one document, an array giving its
  elements, so the `json` types of `to_json` and `from_json` undo each
  other, as their defaults do.
- [x] **D7.** How are the encoder's options given, and what's the text's
  encoding? **`json => {...}`, passed to `JSON::MaybeXS->new` over the
  defaults `utf8` and `allow_nonref`, or `json => $object`, used as it
  is,** Iain decided on 2026-11-14. Text is UTF-8 bytes, as
  `encode_json` and `decode_json` have it, and files are opened `:raw`.
  Unknown options croak.
- [x] **D8.** Where does it live, and how does it export? **As
  Ekorn::Pipeline::JSON, exporting `from_json` and `to_json` on request,
  and from Ekorn::Pipeline::Tooling, by a `:json` tag and `:all`,** Iain
  decided on 2026-11-14. JSON.pm exports a `from_json` and `to_json` of
  its own by default, so a module using both imports one by another
  name, or calls it by its full name.
- [x] **D9.** One pair of functions with a `type` option and rules for
  working out the format, or a pair for each format? **A pair for
  each, `from_json` and `to_json` for one document, and `from_jsonl`
  and `to_jsonl` for JSON Lines, with `from_json` strict,** Iain
  decided on 2026-11-14, once the first was built: "from_jsonl,
  from_json and to_jsonl, to_json would have saved much buggering
  about". The name says the format, so the `type` option, the rules
  by a file's name, and reading's holding back of the first document
  to see whether it's an array alone all went, and with them the one
  surprise: a `.jsonl` file holding one array read differently from
  the same text in a `.json` file. `from_json` reads one document,
  an array giving its elements, and croaks at a second, pointing to
  `from_jsonl`; `from_jsonl` keeps arrays whole. As stages, `to_json`
  gathers every value into one array, and `to_jsonl` gives a line a
  value, so each is undone by its `from_` function. This replaces D2,
  D4, D5 and D6, kept above as they were decided.

## The plan

What: Ekorn::Pipeline::JSON, exporting on request `from_json(%options)`
and `to_json(%options)`. Given `file` or `fh`, `from_json` is a source
and `to_json` a sink giving how many values it wrote; given neither,
each is a stage. Options: `file`, `fh`, `type` and `json`.

Why: so a caller can read and write JSON in a pipeline with no loop of
their own, and so chapter 10 of the how-to can show, step by step, how
a module of parts is put together.

Steps:

1. JSON::MaybeXS into `cpanfile` and the 2026-0025 dependencies.
2. The module, built from `source`, `gather` and `sink_one`, with its
   POD and DIAGNOSTICS, and its tests, run under Cpanel::JSON::XS and
   JSON::PP, keeping coverage above the floors.
3. Tooling's `:json` tag.
4. The reference, a section for the module; the how-to, a walkthrough
   in chapter 10 of the module's anatomy, and a recipe in chapters 5
   and 6; the README; `Changes`.

Done when the module, its tests and its docs are in, every example
run, with coverage above the floors.

## What happened

- **Outcome:** as Done when. Ekorn::Pipeline::JSON, its POD, and
  `t/24-json.t`, each case run with JSON::MaybeXS's encoder and with a
  JSON::PP object; statements and branches covered in full; the
  reference's section, run by hand; and the how-to's recipes in
  chapters 5 and 6 and its walkthrough in chapter 10, which
  `xt/howto.t` runs. Tests pass on 5.36 to 5.44.
- **Two functions, then four.** It shipped first, in
  aadbc05c3e1f8ffd588351de157d5ed0a2344f5e, as `from_json` and
  `to_json` with a `type` option, reading working out the format from
  the input, and writing choosing by the file's name. D9 replaced that
  with a pair for each format the same day, before any release, so
  nobody saw the first; DBIx-Squirrel, which had a task to expose the
  first, had it updated.
- **Changes from the plan:**
  - The parts are Ekorn's own, made with `source`, `gather`, `stage`
    and `sink_one`, chosen by the options, with no class of the
    module's: one object can't be both a stage and a sink, and a
    source made from a file has no use as a stage, so a function
    making the part its options ask for was simpler, and is what the
    walkthrough shows.
  - The walkthrough builds a cut-down `from_jsonl` and `to_jsonl`, in
    four steps, then lists what the real module adds and why, rather
    than walking through all of it.
- **Found:**
  - JSON::MaybeXS 1.004008 doesn't choose its backend by
    `PERL_JSON_BACKEND`, so the tests give JSON::PP as an object.
  - Both backends' incremental parsers take a number at the end of
    the text as whole, so the sources read a block and on to the end
    of its line, which a number can't cross; lose the documents before
    a malformed one in the same call, which is harmless, as the run
    dies; and croak, asked for the text they hold, inside a document,
    which is how an input that ends inside one is found.
  - Perl::Critic doesn't parse `try`: a sub's last `return`, straight
    after a `catch` block, is taken as part of its statement, and the
    sub as having none, unless a `;` ends the `catch`.
