# 2026-0044. A run fed a value at a time

**Status:** shipped, unreleased

**Decisions:** D1 settled: `$pipeline->feed`, an Ekorn::Pipeline::Feed.
D2 settled: `push` returns what came out of its values. D3 settled:
`close` gives the flushes' values and the sink's result. D4 settled: a
stop ends the run in the push that meets it. D5 settled: once the run
has ended, however, a push croaks. D6 settled: no context, and no
pushing from inside the run, for now, with neither ruled out later. D7
settled: built into the core's loops, unless another way proves
better. D8 settled: a v0.3.x, with a message to DBIx-Squirrel; a
v0.4.0 if the work changes what stages depend on.

**Origin:** roadmap, added 2026-11-16

**Started:** 2026-11-17

**Finished:** 2026-11-17

## Background

A run takes its values in one of two ways today. Pushed, the caller
hands them all over at once, `$pipeline->(@values)`, and gets every
result back. Pulled, an iterator asks its source for each value as its
caller asks for a result. Neither takes values as they arrive, when
something else decides: a library calling back for each row, record
or file it finds (Text::CSV, XML::Twig, `File::Find`, an event loop's
callbacks), or a stage running values through a branch of its own, as
`tee` (2026-0048) does. Today such a caller collects everything first,
or does without stages.

A run fed a value at a time is opened by its caller, fed values one
or a few at a time, getting back what comes out of each, and closed,
getting what the flushes give; its ends are told how it ended. It says
when a stage has stopped it, so a callback can tell its library to
stop too.

What it needs is in the core already. `_full_iterator` in
`lib/Ekorn/Pipeline.pm` runs a run with flushes, ends and sinks,
pulling from its source only when nothing waits in the stages: a
source that could say "nothing yet", rather than "no more", would let
the loop stop between pushes and carry on at the next. `_push_steps`
runs a plain run, with no flush, end or sink, each value through every
step, and a stop's values going on from the step after it; held open
across pushes, it would do the same for a plain fed run.

2026-0048, `tee`, is built on it (its D7), as 2026-0045's
asynchronous runs would be. It only adds, so it's a v0.3.x.

## Decisions

- [x] **D1.** What is it, and what's it called? A method of
  Ekorn::Pipeline, `feed`, returning an object of a new class,
  Ekorn::Pipeline::Feed: one run, made when `feed` is called, so a
  `gather`'s block is called then, and an error in it is thrown then,
  as an iterator's is. Its methods are `push`, `close`, `finish` and
  `ended`, the last two as an iterator's are. As recommended: a feed
  is a run the caller drives, as an iterator is one its caller pulls,
  and it has the same lifetime and names where they mean the same.
  Iain decided on 2026-11-17.
  Other names considered: `open`, which reads as a file's, and
  `writer`, which says nothing of results coming back.
- [x] **D2.** What does `push` return? The results that came out of
  the values pushed, in order, as a list; in scalar context, an array
  reference of them, as an iterator's `all`. A value a stage drops
  gives nothing; one a stage turns into several gives them all. A
  sink's result isn't among them: it's given by `close`. As
  recommended, Iain decided on 2026-11-17: the caller gets what each
  push made, there and then, as a callback needs.
- [x] **D3.** What does `close` do? Ends the input: calls the
  flushes, in order, as a run does when its source runs out, and the
  ends, told how the run ended from where each stands. It returns what
  the flushes give, through the stages after them, and a sink's
  result, as `all` would at the end of an iterator's run; in scalar
  context, an array reference of them. As recommended, Iain decided on
  2026-11-17: it's the end of a pushed run, `$pipeline->(@values)`,
  split from its start.
- [x] **D4.** What does a stop do? It ends the run in the push that
  meets it, as it would end an iterator's: the values it carries go
  on, the flushes after the stage that stopped are called, then every
  end, and that push returns all of it. `ended` says `stopped` from
  then on. As recommended, Iain decided on 2026-11-17: the run's own
  rules, unchanged, and the caller learns at once that it can stop
  feeding, so a callback can stop its library.
- [x] **D5.** What does a push do once the run has ended? It croaks,
  however the run ended: by a stop or a death inside it, or by the
  caller's `close` or `finish`; a second `close` croaks too. So a
  caller feeding values as they arrive asks `ended` before each push,
  or after each, and stops its library when it's defined. `finish`
  ends the run as from outside, as an iterator's does: no flush is
  called, values waiting are dropped, and each end is told how the run
  ended from where it stands, `stopped` if its input hadn't run out. A
  feed let go unclosed is finished, as an iterator let go is. Iain
  decided on 2026-11-17, against the recommendation, which was to drop
  a push after a stop or a death quietly, as an iterator's call gives
  nothing after either: a croak says at once that values are going
  nowhere, where a quiet drop could lose them unnoticed. It's open to
  being reconsidered, if the work shows it's clearly the worse choice:
  if so, What happened says why, and Iain decides again.
- [x] **D6.** Does a feed have a context, and can it be pushed from
  inside itself? No context: `run_context` is undef in it, as in a
  pushed run, until a caller needs one. A `push`, `close` or `finish`
  from one of the feed's own stages, flushes or ends croaks. As
  recommended: a context can be added later without breaking anyone,
  and pushing into a run from inside it would run its stages inside
  themselves. 2026-0046's `result_number` counts each feed's results
  as its own run's, as its D2 says for every run. Iain decided on
  2026-11-17, as recommended, but without painting us into a corner:
  `feed` takes no arguments now, so named options, a context among
  them, can be added later; and a croak can be lifted later, where a
  behaviour, once allowed, can't be taken back.
- [x] **D7.** How is it built? In the core's two loops, not a third:
  a run with a flush, an end or a sink by `_full_iterator`, its source
  able to say "nothing yet", so the loop returns between pushes; a
  plain run by `_push_steps`, its stop state kept between pushes. Done
  when pushed runs and iterators are no slower than at v0.3.5,
  measured as 2026-0040 and 2026-0041 measured them. As recommended:
  one loop for each kind of run keeps what Stop and Gather do the same
  in every run, and DBIx-Squirrel's rows pay for none of it. Iain
  decided on 2026-11-17, with room to be pragmatic: if building into
  the loops proves not the best way, even allowing some slack in the
  constraints, other ways are tried, such as a loop of the feed's own
  sharing the core's helpers, and the record says what each showed.
  "No slower" means within the noise of the measurement.
- [x] **D8.** What version, and what does DBIx-Squirrel get? A v0.3.x:
  it only adds, and changes nothing a stage depends on. DBIx-Squirrel
  gets a message, not a task: `feed` is a method of Ekorn::Pipeline,
  so it reaches its users with no change of DBIx-Squirrel's, and
  nothing it imports changes. As recommended, Iain decided on
  2026-11-17, open to being overruled by what the work finds: if it
  needs an architectural rework that changes what stages depend on,
  such as the order things run in, what Stop or Gather do, or a
  protocol, it's a v0.4.0, with a task for DBIx-Squirrel, as
  [neighbours.md](../claude/neighbours.md) says.

## The plan

**What:** `$pipeline->feed`, returning an Ekorn::Pipeline::Feed, one
run, with `push`, `close`, `finish` and `ended`, as D1 to D6 say,
built as D7 says, in a v0.3.x.

**Why:** nothing takes values as they arrive, from a library's
callbacks or a stage's branch of its own; `tee` (2026-0048) is built
on it.

**Steps:**

1. Measure v0.3.5, best of five, ns a value, 200,000 values, on 5.36
   and 5.44: a plain push; a push through a gather with a flush; an
   iterator's `next` and `all`, plain and with a flush; and a push of
   one value through `take(5)`, ns a push, 100,000 pushes.
2. Write the spec as tests first, in `t/28-feed.t`: what each push and
   `close` return, in list and scalar context; stops, carried values
   and flushes after them; deaths, named as a run names them; each
   croak of D5 and D6; `finish` and a feed let go; how each end is
   told the run ended; plain runs and runs with flushes, ends and
   sinks alike, each giving what `$pipeline->(@values)` gives for the
   same values.
3. Build it into the core's loops: the full iterator's source able to
   say "nothing yet", and `_push_steps`' state kept between pushes.
   Measure; if it costs existing runs more than the noise, or tangles
   the loops, try a loop of the feed's own, and keep the better.
4. Document it: Ekorn::Pipeline::Feed's POD, with DIAGNOSTICS for each
   new message; `feed` in Ekorn::Pipeline's POD; `docs/REFERENCE.md`;
   a recipe in `docs/HOWTO.md`, feeding a pipeline from a library's
   callbacks; the manuals remade; `Changes`, with its precis.
5. Run the tests on every Perl, under yath, `xt/` included;
   `scripts/coverage`, raising a floor if coverage rose; perltidy and
   perlcritic on 5.44.
6. Write DBIx-Squirrel a message, as
   [sessions.md](../claude/sessions.md) says.

**Done when:** a feed runs values through any pipeline as a pushed
run would, its stops, deaths, flushes and ends included; pushed runs
and iterators are no slower than at v0.3.5, within the noise; the
tests pass on every Perl CI covers; coverage keeps its floors.

## What happened

- **Measurements, the baseline,** v0.3.5, whose `lib/` is `develop`'s
  when work started: best of five after a warm-up, two rounds, ns a
  value, 200,000 values, from a source closure over an array for the
  iterators, read with the iterator's code taken once; a one-value
  push, ns a push, 100,000 pushes. On Iain's Mac, on 2026-11-17:

  | | 5.36 | 5.44 |
  |---|---|---|
  | push, a bare stage | 343 to 348 | 388 to 390 |
  | push, a gather with a flush | 671 to 690 | 729 to 731 |
  | `next`, a bare stage | 830 to 843 | 909 to 912 |
  | `next`, a gather with a flush | 864 to 876 | 945 to 948 |
  | `all`, a bare stage | 827 to 849 | 904 to 907 |
  | `all`, a gather with a flush | 847 to 857 | 924 to 926 |
  | a one-value push through `take(5)` | 4,904 to 4,948 | 4,729 to 4,773 |

  So the noise between rounds is up to 3%, and "no slower" (D7) means
  within that. A pushed gather with a flush takes the full loop, at
  about twice a bare stage's cost, as 2026-0041 left it; a pulled run
  costs about the same whichever loop it takes.
- **Outcome:** done, as D1 to D8 settled it. `$pipeline->feed`
  returns an Ekorn::Pipeline::Feed, in `lib/Ekorn/Pipeline/Feed.pm`,
  with `push`, `close`, `finish` and `ended`. `t/28-feed.t` feeds 19
  pipelines, with and without stages whose ends log how they were
  told the run ended, 0, 1 and 10 values, pushed 1, 2 and 10 at a
  time, and expects what an iterator of the same stages gives over
  the same values: the results, `ended`, each end's word, and any
  error; 342 cases, then a subtest for each of D1 to D6. The tests
  pass on every Perl CI covers, under yath and `prove`; coverage keeps
  its floors, with Feed's POD and a `new` documented as made by
  `feed`, as Iterator's is.
- **How it's built (D7):** in the core's two loops, as planned. A run
  with a flush, an end or a sink is an iterator of `_full_iterator`,
  whose source gives what's been pushed; `%run` carries `hungry`,
  true until the feed is closed, and a source with nothing then makes
  the loop return, rather than end, so the next push carries on. The
  check is in the branch taken once a source runs dry, so no other run
  pays for it. A plain run is `_push_steps`, a push at a time: the run
  holds no state between values but its stop, which `_push_steps` now
  records, with a death, in a scalar the feed passes it, `undef` for
  every other caller. To keep perlcritic's count of arguments,
  `_push_steps` now takes a step's names and the pipelines it came
  from as one pair, unpacked only to name a step in an error, built
  once by `new`.
- **Measurements, after,** as the baseline, two rounds, v0.3.5
  alternating with this change:

  | | 5.36 before | after | 5.44 before | after |
  |---|---|---|---|---|
  | push, a bare stage | 337 to 349 | 346 to 352 | 389 to 391 | 388 to 390 |
  | push, a gather with a flush | 669 to 689 | 684 to 691 | 732 to 737 | 731 to 742 |
  | `next`, a bare stage | 840 to 851 | 845 to 850 | 913 to 914 | 913 to 915 |
  | `next`, a gather with a flush | 873 to 881 | 875 to 880 | 953 | 951 to 952 |
  | `all`, a bare stage | 834 to 840 | 837 to 846 | 911 to 912 | 907 to 910 |
  | `all`, a gather with a flush | 857 to 858 | 856 to 858 | 934 to 935 | 928 to 929 |
  | a one-value push through `take(5)` | 5,003 to 5,147 | 4,976 to 5,142 | 4,707 to 4,784 | 4,787 to 4,851 |

  All within the noise, so nothing is slower. A feed, 200,000 values
  pushed one at a time, then closed, best of six: through a bare
  stage, 1,378 to 1,392 ns a value on 5.36 and 1,389 to 1,414 on 5.44;
  through a gather with a flush, 2,032 to 2,036 and 2,049 to 2,057.
- **Changes from the plan:** the feed's own cost was trimmed once it
  was measured. At first, a push through a bare stage cost 1,873 ns;
  most of it is a push's own, as `_push_steps` costs about 1,100 ns a
  call, as much as calling the pipeline with one value. Checking the
  feed is open inline, not by a method, setting a flag rather than
  `local`, and `_push_steps` recording a death as well as a stop, so
  the plain feed needs no `try` of its own, took it to 1,392; and the
  full feed calling its iterator's `all` code directly, not the
  method, took a gather with a flush from 2,497 to 2,036. Going
  further would mean reshaping the loops, which D7 weighed against.
  The feed checks `ended` before its flag, so a flag left set by a
  push that died can't be taken for a call from inside the run.
- **D5 in use:** the croak after a run has ended costs a caller a
  check of `ended` around each push. The how-to's three examples that
  feed values as they arrive, a library's callbacks, a tee and a run
  for each key, each check it in one line, and none found it clumsy,
  so D5 stands.
- **Docs:** Feed's POD, with what a feed makes possible; `feed` in
  Ekorn::Pipeline's POD; in the reference, `feed`, a Feeds section,
  and its diagnostics; in the how-to, feeding values as they arrive
  and stopping when a stage says so, in chapter 2, a library's
  callbacks feeding a function's caller's stages, in chapter 9, and,
  in chapter 10, a tee and a run for each key, built on a feed, as
  what it opens; the README's third way a pipeline runs; `Changes`.
- **What's left:** `tee` is 2026-0048, as a canned stage in Taps, as
  its decisions say; the how-to's version shows the shape. A stage
  routing each value to one of several branches, and the run for each
  key, are ideas not yet on the roadmap. A message tells DBIx-Squirrel
  of `feed`, as D8 says.
