# 2026-0049. Ekorn::Pipeline::CSV: delimited files as sources and sinks

**Status:** shipped, unreleased

**Decisions:** D1 settled: Text::CSV recommended, not required. D2
settled: Ekorn::Pipeline::CSV's `from_csv` and `to_csv`, with JSON's
options. D3 settled: arrays by default, a `header` option for hashes

## Background

Reading a delimited file, CSV or TSV, is the commonest job a source
does in practice. Written by hand on Text::CSV_XS, as a `source { ... }`
that opens the file for each run and closes it at the run's end, it's
about thirty lines, and easy to get subtly wrong. One such source,
reading five TSV files, had two faults found in review, both of the
kind a library gets right once:

- the set-up deleted `has_header` from the options hash it shared
  between runs, so a second run of the same source read the header as
  data;
- `getline` returns undef at the end of the file and on a row that
  won't parse alike, so a malformed row ended the run quietly, as if
  the file were done.

Ekorn::Pipeline::JSON already does this job for JSON and JSON Lines:
`from_json` and `from_jsonl` are sources given `file` or `fh`, and
stages given neither; `to_json` and `to_jsonl` are sinks; a `json`
option takes the encoder's options or an encoder object; and a
document that won't decode croaks with a message of Ekorn's own. A
delimited file is the same kind of thing, so it would follow the same
shape, and nothing about the core would change: it's built on the
source and sink protocols as they are.

Text::CSV uses Text::CSV_XS when it's installed and its own pure-Perl
parser when not, as JSON::MaybeXS chooses for JSON, so it needs no
compiler. Ekorn needs it only for this, which is the case for
`recommends` that `dump_to` made with Text::Redact::Secrets
(2026-0038).

## Decisions

- [x] **D1.** Is Text::CSV required, as JSON::MaybeXS is, or
  recommended, as Text::Redact::Secrets is? Recommended, as Iain
  decided on 2026-11-24: a `recommends` in `cpanfile`, loaded when
  `from_csv` or `to_csv` is first called, croaking with a message
  saying to install Text::CSV if it can't be. Required would have been
  simpler, with no path for its absence and no test of one, but
  recommended keeps Ekorn's rule that it depends on nothing it doesn't
  need to run values through stages, and keeps the dependency from
  DBIx-Squirrel's users, who'd otherwise get it through Ekorn.
- [x] **D2.** Its name and options? As recommended, Iain decided on
  2026-11-24: a module of its own, Ekorn::Pipeline::CSV, exporting
  `from_csv` and `to_csv`, which Tooling exports too, in a `csv` tag
  and its `:all`, as it does JSON's in `json`; with JSON's options:
  `file`, `fh`, and `csv`, Text::CSV's options as a hash reference or
  a parser object. `binary => 1` and `auto_diag` off by default, as
  Ekorn reports its own errors (D5). TSV is `csv => {sep_char =>
  "\t"}`, with no `from_tsv`. Following JSON means one shape to learn
  for both, and the docs of one serve the other; `from_tsv` would be
  a third name in Tooling for DBIx-Squirrel to list, for one option.
- [x] **D3.** Rows as array references, or hash references keyed by
  the header? And is the first row a header by default? As
  recommended, Iain decided on 2026-11-24: a `header` option. Absent
  or false, every row is data, given as an array reference; true, the
  first row names the columns and each row is a hash reference keyed
  by them, through `column_names` and `getline_hr`; `'skip'`, it's
  read and dropped, and rows are arrays. Arrays by default, as a
  file's first row isn't always a header, and a stage that maps
  positions to names is still one line; Text::CSV's own `csv()` reads
  arrays too unless told `headers => 'auto'`.
- [x] **D4.** Should a header's names be the run's context, which a
  source can already give, so a stage can read them while rows stay
  arrays? Yes, as recommended, Iain decided on 2026-11-24: whenever a
  header is read, with `header` true or `'skip'`. It needs nothing new
  of the core, and a stage given rows as arrays can still name their
  columns, or a stage given hashes find the columns' order. The
  context is a hash reference, `{columns => [...]}`, as Iain decided
  the same day when work started, in place of the bare array
  reference first settled: DBIx::Squirrel's sources give
  `{columns => [...], ...}`, and Ekorn's own example of
  `run_context` reads `->{columns}`, so one stage serves both.
- [x] **D5.** How is a row that won't parse reported? As recommended,
  Iain decided on 2026-11-24: a `croakf` message of Ekorn's own,
  naming the file, the line and Text::CSV's `error_diag`, with its
  DIAGNOSTICS entry, as JSON's undecodable documents are; never ending
  the run quietly. Text::CSV's `auto_diag` would report it in
  Text::CSV's words, from inside Text::CSV, and its messages aren't
  Ekorn's to keep stable; a message of Ekorn's own is reported at the
  caller's line, and is one users can match.
- [x] **D6.** Given neither `file` nor `fh`, should `from_csv` be a
  stage parsing each value, as `from_json` is? As recommended, Iain
  decided on 2026-11-24: a stage parsing each value as a whole text,
  giving each row it holds, which suits a value that's a file's
  contents; a stage of one line at a time is the caller's, with
  Text::CSV's `parse`. A quoted field can hold a newline, so a value
  of one line isn't always one row, and a stage that took it for one
  would split such a row, or croak on it.
- [x] **D7.** Is `to_csv`, a sink writing rows, part of this item, or
  one of its own? Part of this item, as recommended, Iain decided on
  2026-11-24: the two share their options and their errors, as JSON's
  did when they shipped together, and a module that reads a format it
  can't write would be half a module. With it, this item's size is
  M (3); `from_csv` alone would have been S (2).
- [x] **D8.** How does `to_csv` write hashes, and a header line? A
  hash has no column order. As recommended, Iain decided on
  2026-11-24, when work started: a `header` option. Absent or false,
  no header line, and rows must be arrays; an array reference of
  names, that header line, with hashes written in its order; true,
  the names from the run's context's `columns`, croaking if it has
  none, so `from_csv(header => 1)`, stages, then `to_csv(header => 1)`
  keeps the columns and their order. Sorting a hash's keys was
  weighed: simpler, but it loses the source's order.
- [x] **D9.** How are files' texts encoded? Text::CSV doesn't decode,
  as JSON's decoder does, and the TSVs that prompted this are UTF-8,
  some titles not ASCII. As recommended, Iain decided on 2026-11-24:
  files are opened `:encoding(UTF-8)`, so fields are characters, and
  an `encoding` option names another, such as `latin1`, or `raw`, for
  bytes. A filehandle is used as it is, its layers its opener's.
- [x] **D10.** With `header => 1`, two columns of one name would have
  `getline_hr` keep only the last one's value, quietly. As
  recommended, Iain decided on 2026-11-24: `from_csv` croaks on a
  header naming a column twice, when rows are hashes. Empty names are
  allowed, as Text::CSV allows them, as only a duplicate loses data;
  with `header => 'skip'`, nothing is checked.
- [x] **D11.** Can `from_csv` make a header's names into names a
  caller can use, such as placeholders? DBIx-Squirrel's message of
  2026-11-24 (DBIx-Squirrel 7f79ef6dff98679f959b89c9c288c7fa82ae0ed2)
  notes that from its v3.5.0, `execute_for_fetch` takes a hash row for
  named placeholders, so `from_csv` with a header, `batch`, then
  `execute_for_fetch` loads a file with no reshaping, but only if each
  name is a placeholder's: "Track Name" isn't. As recommended, Iain
  decided on 2026-11-24: a `munge` option, taking Text::CSV's
  `munge_column_names` values, `lc`, `uc`, `db`, `none`, a hash
  reference mapping names, or a code reference; `none` by default.
  It's applied with `header` true or `'skip'`, so the context's
  `columns` are munged too, and D10's check is of the names munged,
  as munging can make two names one. `db`, lower case with each run
  of non-word characters an underscore, makes "Track Name"
  `track_name`. A stage renaming keys was weighed: it works, but
  every caller loading a file into a database would write it.

It only adds, so it's a v0.3.x however D1 is settled. It still needs
a message to DBIx-Squirrel, as
[neighbours.md](../claude/neighbours.md) says: `from_csv` and `to_csv`
added to Ekorn's Tooling turn DBIx-Squirrel's `xt/ekorn-tooling.t` red
until it lists them, and the names mustn't clash with one of its own.
With Text::CSV only recommended (D1), its users install nothing new.

## The plan

**What:** Ekorn::Pipeline::CSV, as D1 to D11 say: `from_csv` and
`to_csv`, each a source or a sink given `file` or `fh`, and a stage
given neither, with the options `file`, `fh`, `csv`, `header`,
`munge` (`from_csv` only) and `encoding`. Text::CSV is loaded when one
of them is first called, and its absence croaks then, at the caller's
line. Tooling exports both in `:csv` and `:all`.

**Why:** a delimited file is the commonest source written by hand, and
easy to get subtly wrong. jdc-lab's UKSOC module, reviewed on
2026-11-24, read a header as data on a second run and ended quietly at
a row it couldn't parse.

**Steps:**

1. Write the spec as tests, in `t/30-csv.t`, from JSON's in
   `t/24-json.t`: reading a file, a filehandle and a value; rows as
   arrays, hashes or with the header skipped; the context's
   `columns`; `munge`'s settings; a duplicate name croaking; a row
   that won't parse croaking, naming the file and record; a second
   run of one source reading the header again; a stop closing the
   file; UTF-8, `latin1` and `raw`; writing arrays and hashes, a
   header given or from the context, and a round trip; TSV; every
   message at the caller's line. And in `t/31-csv-without-text-csv.t`,
   each function croaking with Text::CSV hidden, as `t/26` hides
   Text::Redact::Secrets.
2. Build it, after Ekorn::Pipeline::JSON's shape: its per-row
   closures reading `$_[0]`, the module in
   `@Ekorn::Pipeline::Errors::INTERNAL`, `Text::CSV` a `recommends` in
   `cpanfile`, and `Build.PL` and `META.json` remade.
3. Prove it on jdc-lab's UKSOC: rewrite it on `from_csv`, keeping
   `perl/lib/UKSOC.pm.bak`, the hand-written source, as the reference,
   and check both give the same rows, from every file. Time reading
   `entries.tsv`, 32,670 rows, both ways.
4. Document it: the module's POD, with DIAGNOSTICS; Tooling's POD and
   the README's list of modules and tags; the reference's section,
   module table and index; how-to recipes to read and write CSV and
   TSV, run by `xt/howto.t`; the manuals remade; `Changes`.
5. Run every check: the tests on every Perl CI covers, coverage
   against its floors, Perl::Critic and Perl::Tidy on 5.44, the
   spelling, and gitleaks.
6. Write DBIx-Squirrel a message naming `from_csv` and `to_csv`, for
   its `xt/ekorn-tooling.t`, and `munge => 'db'` for its recipe.

**Done when:** the module ships with its tests, run with Text::CSV and
without it, keeping coverage above its floors; with its POD,
DIAGNOSTICS, and sections in docs/REFERENCE.md and docs/HOWTO.md; with
its line in `Changes`; UKSOC reads the same on it as by hand; and
DBIx-Squirrel has its message.

## What happened

- **Outcome:** shipped, unreleased, as Done when asks, but for the
  message to DBIx-Squirrel, sent once this is pushed. Ekorn::Pipeline::CSV's
  `from_csv` and `to_csv` are as D1 to D11 say, with
  `t/30-csv.t` run on Text::CSV's parser and on Text::CSV_PP's, and
  `t/31-csv-without-text-csv.t` with Text::CSV missing, and failing
  to load. The tests pass on every Perl from 5.36 to 5.44, under
  `prove` too, and on the pure-Perl backend alone; coverage keeps
  every floor, the module at 100% on each measure.
- **Proved on jdc-lab's UKSOC,** rewritten on `from_csv`, its three
  hand-written sources one call. Its tables, from five TSV files, are
  the same, compared byte for byte in a 14 MB dump of every one,
  the 33 fields holding characters that aren't ASCII included.
  Reading `entries.tsv`, 32,670 rows, seven times each way, the median
  was 2.24 µs a row by hand and 2.42 with `from_csv`; read `raw`,
  2.36. So the UTF-8 layer costs about 0.07 µs a row, and the `try`
  that turns a row's decoding error into a message of Ekorn's, with
  the byte order mark's check, about 0.12.
- **Changes from the plan,** each found by the tests:
  - Text::CSV_XS 1.65's `combine` gives bytes, characters or a
    mixture of the two as its fields' UTF-8 flags vary: a field of
    "é" without the flag beside one of "☺" gave half Latin-1 and half
    UTF-8. Text::CSV_PP gets it right. So `to_csv` gives `combine`
    only bytes, each field encoded as UTF-8 first, or checked as bytes
    for `raw`, and decodes or encodes the line it gives, which is the
    same from both backends whatever the flags.
  - An output layer of `:encoding(latin1)` only failed as the file
    closed, with Perl's "Close with partial character", and `raw`
    only warned of a wide character. So `to_csv` writes `:raw` and
    encodes each line itself, and a character the encoding can't hold
    croaks at its row. Reading keeps the layer, as its errors come at
    the row, made to croak by PerlIO::encoding's `fallback`, which the
    module loads up front: it sets its own default when it loads, at
    the first `:encoding` open, which would otherwise undo ours.
  - Both backends decode valid UTF-8 in a field by default
    (`decode_utf8`), so a `raw` file's fields weren't bytes. Ekorn
    turns it off for a `raw` file, and only then: it's what keeps a
    decoded file's fields characters.
  - Text::CSV's `eof` is true after an error too, so the end of the
    input is told from an error by `error_diag`'s code, 2012; and its
    record count runs on across runs of a parser object given, so the
    module counts records itself, for D5's message, which names the
    record, not the line, as a quoted field may hold a newline.
  - Fields are quoted as Text::CSV's defaults quote them, a field with
    a space among them, or holding a byte of 0x7F or above in its
    UTF-8, such as "☺"'s, included; `quote_binary` stays on, as
    Text::CSV_PP stops quoting a field holding a newline without it.
  - A stage's text is read through a small object with a `getline`,
    which both backends read from, rather than a filehandle opened on
    it, whose check of an open that can't fail no test could reach.
- **What's left:** the message to DBIx-Squirrel. Text::CSV_XS's
  `combine` might be worth reporting to its author.
