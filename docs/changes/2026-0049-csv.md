# 2026-0049. Ekorn::Pipeline::CSV: delimited files as sources and sinks

**Status:** open

**Decisions:** D1 open: Text::CSV recommended, or required. D2 open:
its name and options, after Ekorn::Pipeline::JSON. D3 open: rows as
arrays or hashes, and the header. D4 open: the column names as the
run's context. D5 open: how a row that won't parse is reported. D6
open: a stage for each value, given no file. D7 open: `to_csv` in this
item, or one of its own.

**Origin:** roadmap, added 2026-11-24

## Background

Reading a delimited file, CSV or TSV, is the commonest job a source
does in practice. Written by hand on Text::CSV_XS, as a `source { ... }`
that opens the file for each run and closes it at the run's end, it's
about thirty lines, and easy to get subtly wrong. One such source,
reading five TSV files, had two faults found in review, both of the
kind a library gets right once:

- the set-up deleted `has_header` from the options hash it shared
  between runs, so a second run of the same source read the header as
  data;
- `getline` returns undef at the end of the file and on a row that
  won't parse alike, so a malformed row ended the run quietly, as if
  the file were done.

Ekorn::Pipeline::JSON already does this job for JSON and JSON Lines:
`from_json` and `from_jsonl` are sources given `file` or `fh`, and
stages given neither; `to_json` and `to_jsonl` are sinks; a `json`
option takes the encoder's options or an encoder object; and a
document that won't decode croaks with a message of Ekorn's own. A
delimited file is the same kind of thing, so it would follow the same
shape, and nothing about the core would change: it's built on the
source and sink protocols as they are.

Text::CSV uses Text::CSV_XS when it's installed and its own pure-Perl
parser when not, as JSON::MaybeXS chooses for JSON, so it needs no
compiler. Ekorn needs it only for this, which is the case for
`recommends` that `dump_to` made with Text::Redact::Secrets
(2026-0038).

## Decisions

- [ ] **D1.** Is Text::CSV required, as JSON::MaybeXS is, or
  recommended, as Text::Redact::Secrets is? Required is simpler: no
  path for its absence, and no test of one. Recommended keeps Ekorn's
  rule that it depends on nothing it doesn't need to run values
  through stages, and keeps the dependency from DBIx-Squirrel's users,
  who'd otherwise get it through Ekorn. Recommendation: recommended,
  loaded when `from_csv` or `to_csv` is first called, croaking with a
  message saying to install Text::CSV if it can't be.
- [ ] **D2.** Its name and options. Recommendation: a module of its
  own, Ekorn::Pipeline::CSV, exporting `from_csv` and `to_csv`,
  through Tooling's `:all` too, with JSON's options: `file`, `fh`, and
  `csv`, Text::CSV's options as a hash reference or a parser object.
  `binary => 1` and `auto_diag` off by default, as Ekorn reports its
  own errors (D5). TSV is `csv => {sep_char => "\t"}`; a `from_tsv`
  is sugar to weigh, not needed.
- [ ] **D3.** Rows as array references, or hash references keyed by
  the header? And is the first row a header by default? Text::CSV's
  own `csv()` reads arrays unless told `headers => 'auto'`.
  Recommendation: a `header` option: absent or false, every row is
  data, given as an array reference; true, the first row names the
  columns and each row is a hash reference keyed by them, through
  `column_names` and `getline_hr`; `'skip'`, it's read and dropped,
  and rows are arrays. Arrays by default, as a file's first row isn't
  always a header, and a stage that maps positions to names is still
  one line.
- [ ] **D4.** Should a header's names be the run's context, which a
  source can already give, so a stage can read them while rows stay
  arrays? Recommendation: yes, an array reference of the names, when
  a header is read.
- [ ] **D5.** How is a row that won't parse reported? Recommendation:
  a `croakf` message of Ekorn's own, naming the file, the line and
  Text::CSV's `error_diag`, with its DIAGNOSTICS entry, as JSON's
  undecodable documents are; never ending the run quietly.
- [ ] **D6.** Given neither `file` nor `fh`, should `from_csv` be a
  stage parsing each value, as `from_json` is? A quoted field can
  hold a newline, so a value of one line isn't always one row.
  Recommendation: a stage parsing each value as a whole text, giving
  each row it holds, which suits a value that's a file's contents; a
  stage of one line at a time is the caller's, with `parse`.
- [ ] **D7.** Is `to_csv`, a sink writing rows, part of this item, or
  one of its own? JSON shipped both together. Recommendation: both,
  as the options and errors are shared; with it, this item's size is
  M (3), and from_csv alone S (2).

It only adds, so it's a v0.3.x however D1 is settled. It still needs
a message to DBIx-Squirrel, as
[neighbours.md](../claude/neighbours.md) says: `from_csv` and `to_csv`
added to Ekorn's Tooling turn DBIx-Squirrel's `xt/ekorn-tooling.t` red
until it lists them, and the names mustn't clash with one of its own.
If D1 makes Text::CSV required, the message says so too, as its users
would install it through Ekorn.
