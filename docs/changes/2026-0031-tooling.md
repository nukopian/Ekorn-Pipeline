# 2026-0031. Ekorn::Pipeline::Tooling, one module to import from

**Status:** open

**Decisions:** D1 settled: a module of its own, Ekorn::Pipeline::Tooling, so 2026-0022's D30 stands. D2 settled: tags by module, for what callers use to do work, nothing by default. D3 settled: Operators left out, a pragma of its own. D4 settled: before v0.3.0, which depends on it. D5 settled: a tag's names are public, so dropping one is a v0.4.0. None open.

**Origin:** roadmap, added 2026-11-13, from Iain

**Started:** not yet

## Background

What a caller imports is spread over many modules: `Stop` from Stop,
`gather` from Gather, `take` and `take_if` from Stages::Flow, `batch`
from Stages::Batch, `peek` from Stages::Taps, `from_file` from
Sources, `keep_all` from Sinks, and `pipeline`, `stage` and `source`
from Factories. A pipeline with a source, a filter and a sink can need
five `use` lines, and a caller has to remember which module has which
word. Iain found it friction enough not to release v0.3.0 with it.

2026-0022's D30 decided that Ekorn::Pipeline doesn't re-export
`pipeline`: each word lives in one module, so there's one place to
import it from. Ekorn::Pipeline is a class, whose exports are
`is_stage` and `is_sink`; and Factories, Sources and Sinks each load
it, so its loading them would be a cycle.

Checked on 2026-11-13: of every name the modules export, only `gather`
is exported by two, Gather and Factories, and it's the same sub, so
no tag can clash.

## Decisions

- [x] **D1.** Does Ekorn::Pipeline export the words, or a module of its
  own? **A module of its own, Ekorn::Pipeline::Tooling,** Iain decided
  on 2026-11-13, preferring "Tooling" to "Kit". Ekorn::Pipeline stays a
  class, with no cycle in loading, and D30 stands: each word is still
  made in one module, and Tooling is a second, deliberate way to import
  them all.
- [x] **D2.** Which names, under which tags? **Only what a caller uses
  to do work,** Iain decided on 2026-11-13: not `is_stage`, `is_sink`
  or `croakf`, which are for developers extending the package, and
  stay in their own modules. The tags follow the modules:
  - `:core`: `Stop` and `gather`;
  - `:flow`, `:batch` and `:taps`: every name each of Stages::Flow,
    Stages::Batch and Stages::Taps exports, by default or on request;
  - `:stages`: the three together;
  - `:sources` and `:sinks`: every name of Sources and of Sinks;
  - `:words`: every name of Factories;
  - `:all`: all of these.

  `use Ekorn::Pipeline::Tooling;` with no list imports nothing, as
  `@EXPORT_OK` is the rule; names can be asked for one by one too.
- [x] **D3.** Does Tooling put the operators in force? **No,** Iain
  decided on 2026-11-13: Operators stays a pragma of its own, `use
  Ekorn::Pipeline::Operators`, so nobody gets `|` in their scope
  without asking for it by name.
- [x] **D4.** Before v0.3.0, or after it, in a v0.3.x? **Before,** Iain
  decided on 2026-11-13: the friction is enough that he won't release
  with it knowingly. So 2026-0025 depends on this item, and the docs'
  sweep for v0.3.0 can show it where it reads better.
- [x] **D5.** Is what a tag holds part of Ekorn's public contract?
  **Yes,** as Iain is considering a DBIx::Squirrel::Tooling that
  re-exports what Ekorn ships, by these tags, wherever DBIx::Squirrel
  ships no equivalent. So adding a name to a tag, or a tag, is a
  v0.3.x; dropping or renaming one is a v0.4.0, with a task for
  DBIx-Squirrel, as for any public name.
