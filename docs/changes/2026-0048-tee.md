# 2026-0048. tee: a tap that takes a pipeline

**Status:** shipped, unreleased

**Decisions:** D1 settled: named `tee`, not `tap`. D2 settled: in Taps,
exported on request. D3 settled: takes stages or a pipeline, a sink
allowed last. D4 settled: a stop in the branch ends only the branch, a
death the run. D5 settled: the branch's flushes and ends inside the
tee's. D6 settled: the branch gets the value itself, not a copy. D7
settled: built on 2026-0044's run fed a value at a time.

**Origin:** roadmap, added 2026-11-17

**Depends on:** 2026-0044, shipped, unreleased

**Started:** 2026-11-17

**Finished:** 2026-11-17

## Background

`peek`, `count_into` and `dump_to` are taps: each looks at a value
as it goes by and passes it on. A tap that needs more than one step,
such as logging the first five values that pass a test, has no stage
to write it with. A tee would take stages, a branch off to the side,
run each value through them, throw their results away, and pass the
value on unchanged.

A nested pipeline doesn't do this today. A pipeline given as a stage,
or returned by a `gather` block, is spliced into the run (`_make_run`
in `lib/Ekorn/Pipeline.pm`): its results replace the value, and a stop
inside it ends the whole run. A tee needs the opposite on both counts,
and its branch must be one run spanning the outer run, so that
`count_into`, `take` and the flushes see the whole stream:

- running the branch once for each value starts its state afresh on
  every value;
- buffering the values and running the branch in the tee's flush
  gives its side effects at the wrong time, and holds every value.

What it needs is a run fed a value at a time, which is 2026-0044.

It only adds behaviour, so it's a v0.3.x, and DBIx-Squirrel gets a
message, not a task.

## Decisions

- [x] **D1.** What is it called? `tee`, as recommended, Iain decided
  on 2026-11-17: what Unix's `tee` does, a copy off to the side. `tap`
  is already a method of Ekorn::Pipeline::Pipes, meaning much the same
  for an object, and a function `tap` imported into a class inheriting
  from Pipes would replace that method in the class.
- [x] **D2.** Where does it go, and how is it exported? In
  Ekorn::Pipeline::Stages::Taps, exported on request, as `dump_to` is,
  and in `:all` and Tooling's tags, as recommended, Iain decided on
  2026-11-17, as he'd envisioned it: so that loading Taps adds no new
  default name.
- [x] **D3.** What does it take? A list of stages, made into a
  pipeline with `Ekorn::Pipeline->new`, so a pipeline object, being a
  stage, goes too; and a sink allowed last, as in
  `tee(take_if { ... }, to_file($path))`, as recommended, Iain decided
  on 2026-11-17, as he'd envisioned it: the branch takes whatever a
  pipeline takes.
- [x] **D4.** What does a stop or a death in the branch do? A stop
  ends only the branch, and the tee passes values on after it without
  running them through the branch; a death in the branch kills the
  whole run, named as the branch's stage within the tee, as `#2.3` is
  for a gather's pipeline. As recommended, Iain decided on 2026-11-17:
  a tap mustn't cut the main run short, but an error mustn't be lost.
- [x] **D5.** When do the branch's flushes and ends run? Its flushes
  inside the tee's flush, so when the tee's input runs out; its ends
  inside the tee's end, told how the branch ended from where it stands:
  `stopped` if the main run stopped before the branch's input ran out.
  As recommended, Iain decided on 2026-11-17: the branch's lifetime is
  the tee's, so its flushes and ends keep the order a run's have.
- [x] **D6.** Does the branch get a copy? No: the value itself, as
  `peek`'s block does, so a branch that changes a hash changes it for
  the main run too, which the docs say. As recommended, Iain decided
  on 2026-11-17: a deep copy would cost every value, and can't copy
  everything.
- [x] **D7.** What is it built on? On 2026-0044's run fed a value at
  a time, as recommended, Iain decided on 2026-11-17: so the tee is a
  short stage built on a public protocol, and 2026-0044 gets a first
  user. The core's own push steps would ship sooner, but tie a canned
  stage to the core's internals.

## The plan

**What:** `tee(@stages)`, in Ekorn::Pipeline::Stages::Taps, exported
on request and in `:all` and Tooling's `:taps`, as D1 to D7 say: a
stage made with `gather`, which makes a feed of a pipeline of its
stages for each run, pushes each value into it while it's open,
passes the value on unchanged, closes the feed in its flush and
finishes it in its end.

**Why:** `peek`, `count_into` and `dump_to` each do one thing; a tap
of any shape is a pipeline.

**Steps:**

1. Write the spec as tests, in `t/29-tee.t`: values pass unchanged,
   pushed and pulled; the branch sees each value, in order, the same
   value, not a copy; a stop in the branch ends only it; a death kills
   the run; the branch's flushes at the tee's, and its ends at the
   tee's, told how it ended; a sink last; a fresh branch for each run;
   a pipeline given; mistakes croaking at the caller's line; the
   exports.
2. Build it in Taps, its per-value closure reading `$_[0]`.
3. Measure a value through `tee(sub { $_ })` against `peek`.
4. Document it: Taps' POD, with DIAGNOSTICS if it adds a message;
   Tooling's POD; the reference's Taps section and module table; the
   how-to, where the tee built by hand in chapter 10 becomes how the
   canned one works, and recipes for a tee in chapter 1's taps and
   chapter 11's debugging; the manuals remade; `Changes`.
5. Run every check, as 2026-0044 did.
6. Write DBIx-Squirrel a message: `tee` reaches it only if it adds the
   name to what it imports from Taps.

**Done when:** `tee` behaves as D1 to D7 say, the tests pass on every
Perl CI covers, coverage keeps its floors, and the docs show what it
is for.

## What happened

- **Outcome:** done. `tee(@stages)` is in Taps, exported on request,
  in `:all` and in Tooling's `:taps`. `t/29-tee.t` checks the exports;
  values going on unchanged, pushed and pulled, the branch seeing each
  as it's pulled; the branch's results dropped, a sink's included;
  the value itself shared; a stop in the branch ending only it; its
  flushes at the tee's, a sink's result included; its ends, as below;
  a death killing the run; a fresh branch for each run; a pipeline
  given, and no stages; a sink last writing; and a mistake croaking
  at the caller's file. The tests pass on every Perl CI covers, under
  yath and `prove`; coverage keeps its floors.
- **Changes from the decisions, for Iain to confirm before the
  release:**
  - **D4, how a death in the branch is named.** D4 said "named as the
    branch's stage within the tee, as `#2.3` is for a gather's
    pipeline". A feed's run names its stages by their places in its
    own pipeline, and the main run wraps a stage's error in its own
    line, as it does for a pipeline called from a stage, so the
    message is nested: `Pipeline stage #1 failed at ...:`, then,
    indented, `Pipeline stage #2 failed at ...:`, then the error. Both
    lines point at the caller's line. Naming it `#1.2` would need the
    core to let a stage's error say where within it it came from, and
    not wrap it again: a change to how every run reports an error. As
    messages are behaviour DBIx-Squirrel depends on, this is settled
    before the release, not after.
  - **D5, when the branch's ends are called.** D5 said its ends are
    called inside the tee's end. A feed's run calls its ends as it
    ends, as every run does, so they're called in the push that meets
    a stop or a death in the branch, in the tee's flush, whose `close`
    ends the branch, or in the tee's end only if the main run ended
    before either; then they're told `stopped`, even when the main run
    died, as an iterator read as a source is. So a branch's ends are
    called before the main run's when the main run's values run out.
    Holding them back would need a feed whose `close` doesn't end the
    run, which D3 of 2026-0044 ruled out.
- **Measurements,** best of five, ns a value, 200,000 values pushed,
  two rounds, on Iain's Mac:

  | | 5.36 | 5.44 |
  |---|---|---|
  | `peek { 1 }` | 381 to 389 | 426 to 430 |
  | `tee(sub { () })`, through the feed's methods | 2,192 to 2,226 | 2,203 to 2,223 |
  | the same, through the feed's own code | 1,683 to 1,725 | 1,813 to 1,854 |
  | `tee` of a gather with a flush, the feed's own code | 2,255 to 2,281 | 2,403 to 2,471 |

  So the tee calls the feed's `push` and `ended` code directly, as
  `feed` calls its iterator's `all`: the branch can't reach its feed,
  so the checks the methods make, that it's open and not pushed from
  inside, are made by the tee's `$open`, or can't fail. Of what's left,
  about 350 ns is the main run taking its full path, as a tee has a
  flush and an end, and the rest is a push into the branch.
- **Docs:** Taps' POD, with what a tee is for, how its branch runs,
  and what it costs; Tooling's POD and the README's list of modules;
  in the reference, `tee` in the Taps section, with examples, and the
  tables of stages, exports, tags and modules; in the how-to, a
  pointer from chapter 1's taps, "Tap with a pipeline of stages" in
  chapter 11, with a branch noting the first hits, one totalling the
  plays in its flush, and one dumping only the values wanted, chapter
  10's tee by hand now showing how Ekorn's is built, and its cost in
  chapter 12; `Changes`.
- **What's left:** D4 and D5's changes, for Iain, above. A message
  tells DBIx-Squirrel of `tee`, which reaches its users only if it
  adds the name to what it imports from Taps.
